# 对照实验：颜色恢复成红色、“血”保持改成 x，看审核是被颜色还是被“血”字卡的

接着 `20261012-095000-purple-and-x.md`。

## 背景

- 上一轮提交的 **V1.0.3（紫色 + 文字里的“血”改成 x + 新图标）审核通过**。
  再往前：V1.0.2（橘黄色，文字里还有“血”，图标上有“血灾”）未通过；V1.0.1（原来的红色、有“血”字）未通过。
  后台始终只给“内容未通过平台综合审核”一句话，所以“到底是颜色还是‘血’字”没法直接知道。
- 用户的要求：**把所有颜色恢复成红色，再上传一版**，看审核是不是被颜色卡的，还是被“血”这个字卡的。
- 这个实验只改一个变量：V1.0.3 → 新版，只有“颜色”变回红色，文字（x）不动。

## 做法

1. **保留紫色版**：改之前把当前 15 个文件（14 个 `src/` + `styles.css`，加 `minitool.css`）原样快照到 `dev/minitool/_variants/purple-x/`，以后想换回紫色可以直接拷回去。紫色包和图标也都还在：
   `dev/minitool/rusty-lake-minitool-purple-release.zip`、`dev/minitool/_old/icon-purple-x.png`。
2. **颜色 → 原来的红色**：从改色之前的备份还原 14 个文件（`src/` 里 13 个 + `styles.css`；`minitool.css` 的情况见下）。先确认这些文件在我最后一次写入之后没有被别的会话改过（对比 mtime，只有我自己的 `make_icon.py` 和 `minitool.css`）。
   这次读写文件都保留原来的换行：`props_beach.js`、`props_inner.js`、`sky.js`、`styles.css` 原本是 CRLF，之前改橘黄 / 紫色时我的脚本把它们悄悄转成了 LF；这次还原后这四个文件和备份**逐字节一致**。
3. **`minitool.css` 不整份还原**（里面有并行会话的 `--sw/--sh/--fs` 尺寸变量和 `no-flexgap` 兜底，上一轮刚重建过），只把报错横幅的颜色换回原来的 `rgba(130, 24, 24, 0.94)`。
4. **在还原后的原文件上重新做“血 → x”**，6 处文字，和上一轮一致，只有一处措辞不同：木桶那句因为不再是紫色，写成 `暗红色的x灌满了木桶。`（原句 `暗红色的血灌满了木桶。`，只把“血”换成 x）。
   和改色之前的原始备份比较：`src/` 里只剩这 6 处文字不同；`styles.css` 完全一致。演示章节 `_demo.js` 的“红宝石 / Red gem”恢复成原样。
5. **图标**：用红色版重拍记忆场景（UI 隐藏，棺材下是原来的暗红血泊），副标题“第一灾 · x灾 · 3D”换回原来偏红的肉色 `(183,138,122)`。`make_icon.py` 加了环境变量 `ICON_SUB_COLOR`：
   `ICON_SUB_COLOR=183,138,122 python dev/minitool/make_icon.py dev/shots/red-x/icon_scene.png dev/minitool/icon.png`。
6. **打包**：`python dev/minitool/build.py --release --out dev/minitool/dist-red-x-release --zip dev/minitool/rusty-lake-minitool-red-x-release.zip`。

## 怎么解读结果（提前写下来，免得事后改口）

- 红色版**通过** → 颜色不是原因，“血”字（章节名、台词、物品名、图标上的“血灾”）才是；以后保留 x，可以放心用红色。
- 红色版**未通过** → 颜色（血色画面 / 血湖）是原因，或者“颜色 + 文字”都算；那 V1.0.3 的紫色版就是能用的，保持紫色。
- 注意两点：① 这只是单次对照，审核可能有随机性 / 版本间规则变化；② 图标也是审核对象，这次图标是红色版的（和 V1.0.3 的紫色图标不同），所以“颜色”这个变量包括图标里的血泊。
- 如果红色版通过，它会取代当前已通过的紫色版 V1.0.3 成为线上版本；想回到紫色，用 `_variants/purple-x/` 和 `_old/icon-purple-x.png`。

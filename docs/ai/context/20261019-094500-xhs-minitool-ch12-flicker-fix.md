# 小红书小工具：开放第一、二灾，并处理评论反馈的“白屏 / 载入页快速交替闪”

时间：2026-10-19 09:45

## 需求

1. 把当前第一灾和第二灾都能跑通的版本发布到小红书小工具，并在 GitHub 同步。
2. 用户转来一条线上评论：“一进去两三秒就一直闪（白色画面和加载画面快速交替）”，要求查原因，并在这个版本里一起解决。

## 线上现状（2026-10-19 创作者中心）

“锈湖：天堂岛3D”：状态“未通过”（V1.0.5，原因：小工具功能缺陷，可能是页面按钮无法点击），**9.3 万人使用**，生效的是更早通过的 V1.0.4（只有第一灾）。所以评论里的闪屏是线上 V1.0.4 的表现，用户基数很大。

## 评论的诊断

**没能在评论者的手机上复现，原因没有被证实**，下面是证据和判断，不是定论。

证据：
- 页面自己的底色（`html / body / #rot / #stage`）全是 `#000`，所以“白屏”不是我们的页面画出来的，而是容器 WebView 的空白状态（页面没合成出来，或被重载）。
- 游戏代码里启动期不会主动重载页面（整页重载只有两处：菜单里选了另一章、返回标题）。
- 手机视口 + CPU 降速下实测启动期主线程有多条连续的长卡顿（`PerformanceObserver('longtask')`）：桌面速度下最长约 1.2–1.3 秒；CPU 降 4 倍时最长任务中位数约 4.1 秒（3.3–8.2 秒），其中超过 2 秒的有 3–5 个，合计阻塞约 16 秒。V1.0.0 就是因为启动是一条不让出主线程的长任务被判“按钮点不了”，才改成分段启动；那次分得不够细。
- 最大的几块：第一次渲染要同步编译链接 87 个着色器程序（桌面 1.4–1.6 秒，手机 GPU 上更长，期间 GPU 被占满、页面合成不出来）；岛的地形（算顶点到岸线距离 + 画 2048² 地面贴图，桌面约 1 秒、4 倍慢时 6.8 秒）；建筑 / 章节 setup 的整块同步建模；天空的 canvas 2D 贴图。

判断：慢手机上启动期有好几秒不让出主线程 / 占满 GPU，容器或系统把它当成无响应而重载，重载后又重复同样的启动，于是“白屏 ↔ 载入页”反复交替，而且正好发生在启动后两三秒（第一个大卡顿开始处）。这是目前证据最一致的解释，但也可能是内存不足导致 WebView 进程被杀后自动重载（实测内存不算夸张：JS 堆约 51 MB、约 3200 万像素贴图、3 张阴影图）。

## 改动

全部只改小工具打包的副本（`dev/minitool/build.py` 的补丁 + `rotate.js`），**网页版源码一行没动**。

1. **启动再拆细**（`build.py`）：`buildSky`（穹顶 / 全景环 / 远山 / 云按批次）、`buildLake` 前、`buildIsland`（地形的高度循环、距离场、100 万像素着色按行拆开）、`buildBuildings`（每栋建筑之间）、第一灾 / 第二灾章节 `setup` 的每个部分之间，都让出一帧（`window.__RLP_STAGE`）。启动期让出主线程的次数从约 7 次变成约 90 次。
2. **着色器分片预热**（`rotate.js` 的 `__RLP_WARM` + `build.py`）：先 `compileAsync`，再把外景按材质分成约 28 片，每次只让一片可见、渲一帧、累计超过 40 ms 就让出一帧；水面在每一片里保持可见，让倒影那遍渲染的着色器变体也被分摊。最后再整体渲一次（实测只要约 8 ms）。载入页文字同时显示“准备画面 n/28…”进度。
3. **反复重载保护 / 轻量模式**（`rotate.js` + `build.py`）：每次启动记一笔“开始了、没走完”，走完（`RLP.ready` 之后）改成“走完了”；30 秒内连续 2 次发现上一次没走完，这一次进轻量模式：关阴影、像素比降到 1、关水面倒影。只用同步的 `localStorage`，读不了就当没有；正常设备走不到这里。排查面板（连点左上角 5 下）会显示“模式：轻量 / 正常”。
4. **只开放第一灾和第二灾**（`build.py`）：副本里第四灾 / 第五灾不注册 `load`（菜单显示“敬请期待”，代码也不进包）；包体 436 KB。
5. `build.py --no-minify`：不压缩、保留函数名，只用来做 CPU 采样 / 排查，不要上传。
6. `test_minitool.py`：开放章节改为“第一灾,第二灾”；新增“从菜单触摸‘第二灾’（会重载一次页面）”“第二灾完整 autoplay”“启动让出 ≥ 50 次”“反复重载保护”等检查。

## 量化对比（手机视口 + CPU 降速，启动期最长的单个主线程任务）

| | 旧包（V1.0.4 同代码） | 新包 |
|---|---|---|
| CPU 1×（3 轮交替） | 1.17–1.32 秒（>500 ms 的 3 个） | 0.76–0.80 秒（>500 ms 的 1 个） |
| CPU 4×（6 轮交替，地形 / 天空拆分之前） | 中位数约 4.1 秒（3.3–8.2） | 中位数约 2.6 秒（1.7–5.3） |

后续又拆了地形和云，没有再做整套 4× 重复对照；分段计时（等待 / 工作拆开）显示连续计算最长段 1× 在 0.3 秒以内（预热第一步 `compileAsync` 约 1.3 秒除外）、4× 约 1–3 秒。代价：第一屏晚约 0.5–1 秒（1×），总阻塞时间略增（分片渲染的开销）。机器上同时有别的任务时测量噪声很大，所以用交替多轮取中位数。

**没拆掉的**：启动期第一次让出一帧要等一次约 0.75 秒（1×）/ 5–6 秒（4×）——主线程被占着但不是我的 JS，推测是 canvas 2D 贴图 / 合成的一次性开销；`compileAsync` 那一步 1.3 秒。

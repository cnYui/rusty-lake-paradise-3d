# 下载《天堂岛》实况视频作为本地参考（含三个损坏分P的发现与重下）

## 需求

用户给出 B 站视频《【锈湖】天堂岛实况视频（完结）！锈湖系列开坑！》（BV1bo4y1y7fm，UP 主「冰糖柚子茶」，2021-06-11 发布，10 个分P，总长 3:50:30，版权标注为自制），先问能不能下载到本地，确认后要求"全部下载"；下载完成后又回复"重试"。用途用户没有说明；项目是《锈湖：天堂岛》的 3D 复刻，分P 与十灾一一对应（P1 第一灾 … P10 第十灾），按本地参考资料处理。

## 过程与决策

- **可行性（只读）**：本机已有 yt-dlp 2026.08.19 和 ffmpeg 8.0。免登录就能取到 1080P（H.264），「1080P 高码率」需要大会员，没有使用；没有读取任何浏览器 cookie；分享链接里的 `vd_source` 跟踪参数没有使用，请求只用 `BV1bo4y1y7fm/?p=N`。B 站公开接口 `x/web-interface/view` 直接请求会返回 412，分P 标题和时长改从视频网页里解析。
- **位置**：`dev/ref/`。`dev/deploy_mac.sh` 只打包 `index.html`、`styles.css`、`src`、`vendor/three`，放在这里不会传到公网。视频版权归 UP 主，只作本地参考，不要放进 `src/`，也不要随游戏部署或提交。
- **格式**：`bv*[height<=1080][vcodec^=avc]+ba/b[height<=1080]`。P1 同时提供 AV1 流，默认排序会选到 AV1，所以限定 H.264，让 10 个文件编码一致；音频取最高音质 AAC（30280，约 319 kbps）。文件名 `P{NN}_{标题}_BV1bo4y1y7fm.mp4`。
- **下载方式**：单连接约 1 MiB/s，总带宽共享，3 路并行合计约 1.2 MiB/s。中途一度同时开了 3 个按固定顺序下载的进程，发现它们走到后面会撞到同一个分P，停掉后改成 `ForEach-Object -Parallel -ThrottleLimit 3` 的任务队列，P4、P6、P10 靠 `.part` 续传。B 站取格式接口偶发返回空（`No video formats found!`），P1 出现一次、P3 出现两次，重试后成功。
- **第一轮校验不够**：下完后只比对了总时长、分辨率和编码，10 个全部"通过"。随后做 `-c copy` 全量读包和中段 10 秒解码，发现 P09 视频有 H.264 乱包、P10 音频解码报错。
- **定位损坏**：把每个分P 的"视频流 + 音频流下载大小之和"和合并后 mp4 体积对比，正常的只多 0.5–1.0 MiB 容器开销，P06 少 15.8 MiB、P09 少 82.8 MiB、P10 少 87.0 MiB。再用 ffprobe 看两条流各自的实际时长：P06 音频只到 1095.0 s（容器 1530.1 s），P09 视频只到 1295.4 s（容器 2077.1 s，之后是乱码包），P10 音频只到 135.0 s（容器 2432.8 s）。也就是这三个文件各有一条流在下载中被截断或写坏，但 ffmpeg 合并（`-c copy`）没有报错，容器时长仍是整片时长，所以只比对总时长发现不了。
- **原因未确定**：读过已安装的 `yt_dlp/downloader/http.py`——断线后先关文件，再按磁盘实际大小发 Range 请求并核对 `Content-Range` 起点，续传逻辑本身没发现问题；重下时 P10 的音频重试了 11 次、P06 重试了 6 次，最终文件仍然完整，所以"重试"本身不必然损坏数据。怀疑是当时网络不稳时某次 CDN 响应与前半段内容不一致。结论是不能只信下载器报告成功，必须逐流校验。
- **重下与验收**：P09、P10、P06 分别重下到 `dev/ref/_redo/`，验收标准是（a）容器时长与 B 站页面给出的时长相差不超过 3 s；（b）视频流、音频流各自的时长与容器相差不超过 2 s；（c）`ffmpeg -v error -f null -` 完整解码没有任何输出。三个都通过后才换进 `dev/ref/`。
- **旧文件不删除**：损坏的三个旧文件挪到 `dev/ref/_damaged/`（`*.damaged.mp4`，共约 586 MiB），可以整个文件夹删掉。P1–P5、P7、P8 没有动。
- `dev/ref/_redo/` 现在是空目录（尝试删除时被安全检查拦下，空目录不影响使用，可手动删除）。

## 验证

- 10 个文件在最终位置上逐一核对：1920×1080 H.264 + AAC，视频恰为 30.00 帧/秒、音频 46.875 包/秒，两条流的实际时长与容器一致，容器时长与 B 站页面时长相差不超过 1 s。
- 完整解码：P1–P5、P7、P8 无报错（每个 20–70 s）；P06、P09、P10 重下后在 `_redo` 里各做了一次，无报错。
- 没有残留的 `.part`、`.f30080.mp4`、`.f30280.m4a` 临时文件。

校验命令（对每个文件执行，第二条无任何输出才算通过）：

```
ffprobe -v error -count_packets -show_entries format=duration:stream=codec_type,codec_name,duration,nb_read_packets -of json 文件.mp4
ffmpeg -v error -nostdin -i 文件.mp4 -f null -
```

## 注意与已知限制

- 画质是 B 站普通 1080P，不是「1080P 高码率」（需要大会员）。
- 以后用 yt-dlp 下载 B 站分P 视频，下完必须比对两条流各自的时长，以及"视频流 + 音频流大小之和 ≈ 合并后体积"，再做一次完整解码；只看容器时长会漏掉被截断的流。
- 下载期间发现 `dev/ref/` 里多出 `p1`、`p2`、`plague3` 三个目录（不是本次下载创建的，创建时间在下载期间，最后修改到 15:43），内容是从视频抽出的帧和分析笔记，看起来是别的会话在使用，没有改动。
